Forensic read of code only. No fixes, no opinions. File:line citations throughout.

## Q1. M5 wants Truman at the traincar — what removes him from the sheriff map?

**NOTHING.** `js/glue.js:30-38` defines `truman` in the `sheriff` NPCS list with **no `cond` field at all** — the entry has only a `dialogue` cascade. `E.npcActive` (`js/engine.js:337-345`) returns `true` unconditionally when `n.cond` is falsy. The M5 adapter entity that places Truman at the traincar (`js/narrative-engine-adapter.js:195-199`, `map_id: 'traincar'`) is added to a **different map**. `classicIdsFor`/`syncNarrativeEntities` (`js/narrative-engine-adapter.js:336-343`, `:366-389`) only ever touch `GAME.Maps[ent.map_id].npcs` for `ent.map_id` — there is no cross-map bookkeeping anywhere in the adapter. Confirmed empirically: `presence-enumeration.md` shows `truman` at both `sheriff` and `roadhouse` simultaneously in the `act4_afternoon` state (the M5/traincar case is structurally identical — same code path, same absence of a removal mechanism).

## Adapter merge semantics (`js/narrative-engine-adapter.js`)

- **Function**: `syncNarrativeEntities(reason)` (`:366-389`), called from `A.setState` (`:465`), and — per the comment at `:392-398` — wrapped around every `NR.commit*` call so it also runs after every commit; also called with reason `'external'` via `A.syncCarryoverEvidence`.
- **How entities are added**: for each row in the flat `NARRATIVE_ENTITIES` array (`:155-317`), scoped to one `map_id` and carrying one `npc` object, `syncNarrativeEntities` evaluates `when` and pushes/splices `ent.npc` directly onto `GAME.Maps[ent.map_id].npcs` (`:379-380`) — the shared, global, persistent map data structure, not a per-session copy. If the entity's map is also the currently-**loaded live map** (`E.state.mapId === ent.map_id`), the same push/splice is mirrored onto the live engine roster `E.state.npcs` via `hydrateNpc()` (`:381-385`), which reproduces exactly the shape `loadMap` gives a freshly-spawned NPC (`:347-354`, comment at `:345-346` says this is deliberate so an injected entity is "indistinguishable from one placed by loadMap").
- **Same-id classic NPC: replaced or duplicated?** Neither, in the "different id, different map" sense that dominates this audit — but for the "same id, same map" case the adapter refuses to touch it: `classicIdsFor(mapId, map)` (`:336-343`) snapshots, once per map, the ids present in the classic data **before any injection**, and `syncNarrativeEntities` skips any `NARRATIVE_ENTITIES` row whose `npc.id` is in that classic set (`:376`, comment: `"id del gioco classico: mai toccato"`). So within one map, a classic id is never replaced or duplicated by the registry. Across two different maps sharing the same id (Truman/sheriff vs Truman/traincar or /roadhouse; Hawk/sheriff vs Hawk/town), there is **no such protection** — that's the entire duplicate mechanism documented in Q1/Q2/Q4 above.
- **`dialogue: null` entities on interact**: every `NARRATIVE_ENTITIES` row except `ronette`/`infermiera` (which are also `dialogue: null`) sets `dialogue: null`. This is not inert — the comment at `js/narrative-engine-adapter.js:294` states the interaction is owned by a *world-root node* instead (`A.tryInteract`/`A.tryInteractAt`, `:598-676`), which is a separate dispatch path from the classic `dialogue` field. A `dialogue: null` entity is effectively mute to the classic dialogue system; its interaction, if any, comes only from a live world-root node matching that `map_id`/`actor_id` (or `target_id`/`target_kind`) in the current mission.
- **Does the adapter consume classic interacts on tiles it owns?** Not directly — the adapter only manages the `npcs` array; classic `objects`/interact tiles (`js/glue.js` `INTERACT_DLG`) are untouched by `NARRATIVE_ENTITIES`. `A.tryInteract`/`A.tryInteractAt` are a parallel dispatch the engine must call in addition to (or instead of) the classic path — this trace did not locate the engine-side call site that decides which path wins for a given tile/actor; that is outside `js/narrative-engine-adapter.js` and was not audited here (see PART A scope: this file only).
- **`when` re-evaluation cadence**: NOT map-load-only. Per the doc comment at `js/narrative-engine-adapter.js:148-150`, sync happens "ad enable, dopo setState, dopo refreshFromState e dopo OGNI commit" (on `A.enable`, after `A.setState`, after `A.refreshFromState`, and after every narrative-runtime commit) — i.e., on every narrative-state-changing action, not per frame and not only on map load. There is no polling; `syncNarrativeEntities` is event-driven off state mutation, not off a game loop or `loadMap`.
