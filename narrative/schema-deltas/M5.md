# Schema-delta M5 — estensioni generiche proposte (C5-A)

Contratto delle estensioni che M5 richiede al runtime. **Nessuna riga di runtime è
stata modificata**: questo documento è la specifica da approvare prima di C5-B.
Regola guida (dal contratto C5-A): ogni estensione è **generica e dichiarativa** —
nessun `if (mission === 'M5')` esisterà mai nel runtime.

## 1. Valori tipizzati (`state.values`)

**Perché**: `m5_initial_theory`, `m5_final_theory`, `s1` sono valori a dominio
chiuso; rappresentarli come gruppi di booleani creerebbe combinazioni impossibili
(due teorie vere insieme) — vietato dal contratto.

**Stato**: nuovo campo `values: {}` in `createState()`. Un valore assente è
`undefined` (mai una stringa sentinella). Lettura PURA: `NR.peekValue(state, name)`.

**Enumerazioni**: ogni nome di valore DEVE avere il suo dominio in
`state-enums.json → enums` (già presenti: `m5_theory`, `s1`). Il mapping
nome→enum vive in una nuova sezione `values_allowed` (diff allegato). Il
validatore fallisce su valore senza dominio o assegnazione fuori dominio.

**Effetti** (transazionali, applicati SOLO nei commit, come ogni effetto):
```json
{ "value": "m5_initial_theory", "to": "degeneration" }
{ "value": "m5_final_theory", "from_value": "m5_initial_theory" }
{ "value": "m5_final_theory", "opposite_of": "m5_initial_theory", "within": ["degeneration", "staging"] }
```
- `to`: assegnazione letterale (validata contro il dominio).
- `from_value`: copia da un altro valore (Lock B8b: «Mantengo» → final = initial).
- `opposite_of` + `within`: l'altro elemento di una coppia dichiarata (Lock B8b:
  «La rivedo» → l'altra teoria; con due sole teorie la scelta è determinata,
  nessun sotto-menu). Errore di prepare se il valore sorgente è assente o fuori
  da `within`.
- Politica di riscrittura: come le proposizioni — un valore già scritto NON viene
  riscritto (write-once); un secondo tentativo è `repeated` a livello di
  transazione, mai una mutazione.

**Condizioni** (pure):
```json
{ "value_set": "m5_initial_theory" }
{ "value_is": { "name": "m5_final_theory", "equals": "degeneration" } }
```

**Save/load**: `values` entra nei campi obbligatori di `deserialize`. È
l'UNICO campo nuovo dello stato: le milestone sono derivate (niente
`milestones_done`), i tentativi dei confronti vivono nel già-esistente
`comparisons[node].attempts`.
**Migrazione dal vecchio stato M4**: un envelope salvato prima del delta non ha
`values` → la migrazione (esplicita, nel loader di NarrativeSave, versionata da
`narrative_schema_version` 1.0.0 → 1.1.0) aggiunge `values: {}`. Nessun altro
campo cambia. Un envelope 1.1.0 caricato da un runtime 1.0.0 viene RESPINTO
(già garantito dal controllo di versione B5.1).

## 2. Gruppi di osservazione + milestone post-commit

**Perché**: l'avanzamento M5 conta TRE GRUPPI (ticket/ring/scene), non cinque
evidenze; e il Lock impone teoria dopo il 2° gruppo e revisione dopo il 3°,
entrambe bloccanti.

**Dati** (mission-level, già nel JSON proposto):
```json
"observation_groups": { "set_id": "m5_observations", "groups": { "ticket": [...], "ring": [...], "scene": ["E_SCENE"] } }
"milestones": [
  { "id": "...", "node": "m5_theory_initial", "group_set": "m5_observations", "after_groups": 2,
    "resolved_when": { "value_set": "m5_initial_theory" },
    "blocks": { "kind": "observation_group_prepare", "set": "m5_observations" } },
  { "id": "...", "node": "m5_theory_revision", "group_set": "m5_observations", "after_groups": 3,
    "resolved_when": { "value_set": "m5_final_theory" },
    "blocks": { "kind": "node_prepare", "nodes": ["m5_report_intro"] } }
]
```

**Semantica proposta**:
- Un gruppo è COMPLETO quando tutte le sue evidenze sono vere (le evidenze si
  scrivono solo dopo l'ultima pagina del nodo, invariato). Lettura pura:
  `NR.groupsCompleted(state, mission, set_id)` → numero di gruppi completi.
- Una milestone diventa PENDING nell'istante del commit che porta i gruppi
  completi a `after_groups`. La RISOLUZIONE è DERIVATA, mai registrata: la
  milestone è risolta quando `resolved_when` (es. `value_set:
  m5_initial_theory`) è vero — cioè quando la SCELTA ha scritto il valore, non
  quando il nodo-prompt è stato committato. Nessun `milestones_done` nello
  stato: pending = soglia raggiunta ∧ resolved_when falso. (Correzione dalla
  revisione C5-A: il commit del nodo non può risolvere la milestone con il
  valore ancora assente.)
- **Blocco `observation_group_prepare`**: mentre la milestone è pending,
  `prepareNode` di qualunque nodo con `observation_group` dello stesso set
  restituisce `{ ok:false, error:'milestone_pending: <id>' }` (il 3° gruppo
  non si apre nemmeno prima della teoria — niente pagine mostrate e poi
  rifiutate).
- **Blocco `node_prepare`**: idem per i nodi elencati (il rapporto non si apre
  con la revisione pendente).
- **Apertura obbligatoria**: al commit che rende pending una milestone,
  l'adapter apre il nodo-milestone NELLA STESSA SESSIONE (lease tenuto, zero
  frame di gameplay) — stessa disciplina della domanda forzata di Ronette.
  Escape/blur sul nodo-milestone: abort puro; la milestone resta pending e i
  blocchi restano attivi (anti-softlock: il nodo resta sempre riapribile dal
  taccuino e si ripropone alla prossima interazione col set).
- I nodi-milestone sono nodi normali (`kind: "choice"`, `role: "theory"`
  informativo, canale notebook): pagine, scelte, transazioni, save-gate —
  tutto invariato.

## 3. Binding world oltre gli NPC

**Perché**: in M5 l'informazione è ambientale — mucchio, anello, disposizione,
cartelli. Coordinate hardcoded nel nodo narrativo sono vietate dal contratto.

**Dati** (per nodo):
```json
{ "channel": "world", "map_id": "traincar", "target_kind": "object|landmark|actor|sign", "target_id": "ring" }
```
- `actor_id` resta com'è per gli NPC (retro-compatibile: `target_kind:"actor"` è
  un alias dichiarato; M4 non cambia).
- La RISOLUZIONE `target_id → posizione/entità della mappa` appartiene
  all'ADAPTER (C5-C): una tabella per-mappa `world_targets` (es. `ring` → object
  della mappa traincar) — l'identità sta nei dati della mappa, il nodo narrativo
  conosce solo l'id logico. `worldRoots` viene esteso con firma
  `(state, mission, mapId, targetKind, targetId)` mantenendo la firma attuale
  come alias per gli actor.

## 4. Pagine per-valore + rapporto diviso (correzione dalla revisione)

**Perché**: B9 varia UNA pagina per teoria (3 casi), poi riconverge; e la scelta
S1 sta in MEZZO alla sequenza. La forma monolitica prometteva semantiche
incompatibili (widget invariato ∧ unico commit finale): il rapporto è quindi
DIVISO in tre nodi, ognuno con la SUA transazione già validata:

```
m5_report_intro  (dialogue, world)  : p01-p02 → pages_by_value → p03-p05 → next: m5_s1
m5_s1            (choice, internal) : widget B1 INVARIATO — feedback S1 visibile
                                      con s1 ancora null → commit S1 → goto
m5_report_close  (dialogue, internal): p06-p07 → commit del ramo →
                                      east_route_confirmed (unico writer)
```

`pages_by_value {value, cases}`: `prepareNode` seleziona
`cases[peekValue(state, value)]` e concatena a `pages` + `pages_after_branch`;
il validatore esige copertura TOTALE del dominio. Screen-truth garantita per
composizione: feedback S1 → s1 null → commit; pagine finali → east_route
false → commit del ramo → obiettivo OEJ.

## 5. Registro cross-mission dei confronti latenti

**Decisione richiesta dal contratto (punto 7)** — proposta APPROVATA in
revisione: **registro globale delle azioni del taccuino**.
`NR.notebookActions(state, missions)` accetta una missione O una lista
(`missions = Array.isArray(missions) ? missions : [missions]` — l'API M4 a
missione singola resta valida). Aggrega i comparison SOLO dalle missioni la cui
`entry_condition` è vera (le missioni future caricate nel bundle restano
invisibili) più i confronti già aperti nello stato; conserva `source_mission`
per ogni azione; dedup per `node_id` (id duplicati fra missioni = errore del
validatore). Il confronto E7A↔E5 resta selezionabile anche dopo l'ingresso in
M6, finché non eseguito. Motivazione: nessuna scomparsa silenziosa al cambio missione, nessun
flag di travaso, e il taccuino resta derivato dai dati. L'alternativa
(permanenza fino all'ingresso in M6) scarterebbe il confronto a un confine
arbitrario. Registrata qui come decisione da approvare.

## 5b. Ripresa dopo abort: completion_when e repeat_when (C5-A.2)

**Problema** (dalla revisione v1.1): un choice-node composto (pagine → commit →
widget) può risultare `nodes_done` con la scelta ancora non fatta (Escape/blur
sul widget). Con `effect_policy: once` il nodo restituirebbe il repeat al posto
del widget → softlock.

**Contratto generico**:
```json
"completion_when": { "value_set": "m5_initial_theory" }   // sul choice-node
"repeat_when":     { "flag": "east_route_confirmed" }     // sul world-node con next
```
- `completion_when` (choice-node): il nodo è RISOLTO solo quando la condizione è
  vera. Se `nodes_done` ∧ completion_when falsa → prepareNode NON restituisce il
  repeat né le pagine-prompt: riapre DIRETTAMENTE il widget delle scelte.
- `repeat_when` (world-node con continuation): il repeat appare SOLO quando la
  condizione è vera; se il nodo è committato ma la catena è incompleta,
  l'interazione riprende dal `next` (per il rapporto: m5_s1), mai dal repeat.
- `mandatory_beat` vive sul nodo che CONCLUDE la catena (m5_report_close), mai
  sui prompt: beats_completed non registra beat a metà.

## 6. Che cosa NON cambia

Transazioni prepare/commit, letture pure al primo accesso, one-shot/stale,
lease annidabile, hide_attempted_results, comparisons{}, presentazioni,
NarrativeSave (salvo migrazione §1), disciplina participant-facing (nessun ID,
nessun reason code, nessuna parola di design a schermo). Il runtime resta UNO,
condiviso da test e motore.

## 8. Correzioni recepite dalla revisione C5-A (v1.1)

- **Milestone risolte dai valori** (`resolved_when`), mai dal commit del
  prompt; `milestones_done` ELIMINATO dallo schema; migrazione ridotta al solo
  `values: {}`.
- **Rapporto B9 diviso** in `m5_report_intro` (dialogo) → `m5_s1` (nodo-scelta
  interno, widget B1 DAVVERO invariato: feedback visibile con s1 ancora null,
  commit dopo, goto) → `m5_report_close` (ramo interno: p06-p07, poi
  `east_route_confirmed` al commit del ramo — unico writer).
- **Tentativi per-comparison**: `rules.attempt_scope: "comparison"` →
  `comparisons[node.id].attempts`; `track_assistance: false`; il runtime filtra
  su quello, mai su un nome di campo globale; `b8_attempt_history` e
  `assistance_level` restano privati del tutorial M4.
- **Confronti senza scelte**: `comparison_completion: "node_commit"` — al
  commit il confronto diventa `completed` con `result` dichiarato
  (`RECURRENCE_NOT_IDENTITY`), e scompare dalle azioni (anche cross-mission).
- **Kind normalizzati**: `choice` (+`role: "theory"` informativo), `dialogue`,
  `comparison` — nessun kind nuovo `report`.


## 9. Correzioni C5-A.2 (v1.2)

- Domini DISTINTI: `m5_initial_theory_domain` (2 valori) vs
  `m5_final_theory_domain` (3) — «open» impossibile nel valore iniziale anche
  per deserialize, migrazione, save corrotto o effetto errato.
- `completion_when` su m5_theory_initial / m5_theory_revision / m5_s1;
  `repeat_when` su m5_report_intro; mandatory_beat spostato su m5_report_close.
- Registro cross-mission: API retro-compatibile, filtro per missioni ENTRATE,
  6 gate dedicati (single_mission_api_still_works, future_mission_comparisons_hidden,
  entered_mission_comparisons_visible, m5_comparison_survives_into_m6,
  duplicate_node_id_across_missions_fails, completed_cross_mission_comparison_hidden).
- Il conteggio dei controlli statici è PRODOTTO dal validatore a ogni run —
  i documenti non mantengono numeri a mano.
